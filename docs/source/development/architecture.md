# Architecture

tessera is a dual-stack plugin for JupyterHub: a TypeScript/React frontend
shipped as a prebuilt JupyterLab extension, and a Python backend that runs
as a JupyterHub Service. This page describes how the pieces fit together
at deployment time and which security invariants hold across them.

## The three surfaces

| Surface   | Stack            | Role                                                                                    |
| --------- | ---------------- | --------------------------------------------------------------------------------------- |
| Frontend  | TypeScript/React | Per-server status button (green/red), shipped as a prebuilt extension.                  |
| Service   | Python 3.10+     | JupyterHub Service: OAuth flow, encrypted token store, status endpoints.                |
| Admin CLI | Python (Typer)   | Deployment helpers: `config-snippet`, `init-config`, `doctor`, `install-kernel-config`. |

The flow logic (state, PKCE, pending flows, client secrets, token store,
orchestration) is plain Python, callable without tornado; see
{doc}`../api/flow` and {doc}`../api/store`. The HTTP endpoints wire that
flow layer to JupyterHub-authenticated tornado handlers, and
`python -m tessera.service` runs the assembled Service (see
{doc}`../api/service`).

## Where everything runs

```text
┌─────────────────┐          ┌──────────────────────────────┐
│ User's browser  │          │ Hub host                     │
│                 │          │                              │
│ JupyterLab      │   HTTP   │ JupyterHub                   │
│  └─ tessera     │─────────>│  └─ tessera Service          │
│     button      │          │      ├─ SQLCipher database   │
│ (boolean status │          │      └─ owner-only key file  │
│  only, never    │          └───────────────┬──────────────┘
│  a token)       │                          │
└────────┬────────┘                          │ back-channel
         │                                   │ code exchange
         │ authorization redirect            ▼
         │                          ┌───────────────────┐
         └─────────────────────────>│ OAuth2/OIDC       │
                                    │ provider          │
                                    └───────────────────┘
```

- The browser runs JupyterLab and the tessera button. It only ever sees a
  boolean status; no token, state, or verifier transits through it.
- The Service runs as a process managed by the Hub, on the Hub host. The
  SQLCipher database and its encryption key file live on that host, and the
  key is held outside the database (owner-only file, environment variable,
  or SOPS file; see {doc}`../guide/configuration`).
- The identity provider is external. The code exchange happens back-channel
  between the Service and the provider, never through the browser.

## The authorization-code flow, step by step

1. **Login.** The user opens the login URL for a server (the red button is
   a shortcut to it). The Service resolves the server, generates a fresh
   anti-CSRF `state` and a PKCE verifier, and builds the authorization URL
   itself with the S256 challenge. The pending flow (one-shot, TTL-bound,
   bound to the JupyterHub username) is registered last, so a failed OIDC
   discovery leaves nothing behind.
2. **Authorize.** The browser is redirected to the provider's authorization
   endpoint and the user authenticates there. tessera never sees the user's
   provider credentials.
3. **Callback.** The provider redirects back to the fixed callback URL with
   `code` and `state`. The Service validates sizes first, consumes the state
   exactly once, and checks that the flow was registered by the same user.
4. **Exchange.** The Service exchanges the code at the token endpoint, back
   channel, sending the client secret and its PKCE verifier.
5. **Store.** The refresh token is stored encrypted at rest, keyed by
   (username, server), and the button turns green.

## The pull model

The button never orchestrates anything. It consumes a boolean status and,
when red, opens the navigable login URL for its server. There is no token
push toward the frontend: consumers (kernels, clients) pull what they need
from the Service, which is the only component holding secrets.

## Security invariants

- **The redirect URI is configuration, never input.** It derives from
  `service.public_url` plus a fixed service path; no request parameter can
  influence it.
- **The state is one-shot and user-bound.** A callback is accepted only if
  its state consumes a pending flow registered for the same username.
  Replayed, expired, oversized, or foreign states are rejected and logged
  as categorized security events, never with their values.
- **PKCE is tessera's.** The verifier is generated by the Service, the S256
  challenge goes into the authorization URL, and the verifier is only sent
  on the back-channel exchange.
- **The refresh token never reaches the client.** It is encrypted at rest
  in a SQLCipher database whose key is held outside the database, is only
  ever passed as a bound query parameter, and is never logged.
- **No secret in logs or messages.** State, code, verifier, tokens, and
  client secrets never appear in a log line or an error message, on either
  stack, at any log level.
